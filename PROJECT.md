Custom bootloader for the Arduino UNO R4 Minima (Renesas RA4M1): a fork of
Arduino's stock TinyUSB DFU bootloader with five added features:
- flashing an application `.bin` over classic CAN on D4/D5;
- flash-time-configurable USB DFU manufacturer/product names;
- per-device CAN update IDs, so multiple boards can sit in bootloader mode on
  one bus and be addressed individually;
- recovery from an interrupted flash: an update-in-progress marker, the app's
  vector words written only at commit, and a 20 s CAN idle timeout park the
  board in DFU + CAN instead of booting a half-written image;
- a checked USB DFU session.

USB DFU and CAN never write flash at the same time. The image is 15,236 of
16,384 bytes; some code also fills the 0xC0–0x3FF gap below the option bytes.

## Architecture Overview

- **src/** — The bootloader's own C11 sources:
  - a hardware-free, host-testable logic core (`boot/`): partition constants and `BOOT_LOW_FLASH` placement, the image record + update-in-progress marker, CRC32, image validation with `boot_decide()` / `update_start_plan()` / the staged-commit check, the CAN Update Protocol v1 engine (frame filtering, retry re-ACKs, flash-owner hooks), and DFU config parsing;
  - one polled RA4M1 CAN0 driver (`drivers/`) with automatic bus-off recovery, SJW 4 timing and DWT-based timeouts.
- **tests/** — Standalone CMake/CTest project building `src/boot/*.c` as a library and running 100 Unity tests on x86, covering every `boot_decide()` and `update_start_plan()` outcome, the CAN engine and config parsing. No target hardware required.
- **tools/** — Host-side python-can CLI/TUI (`can-flash/`) that flashes an application image over CAN (Protocol v1, the same one in `src/boot/can_update.c`). It can also identify (`--info`), scan (`--scan`) and remotely reboot boards into the bootloader (`--enter-bootloader`).
- **docs/** — Build/flash guide (size gate, option-byte check, boot decision, checked DFU session, update marker and deferred vector unit, idle timeout, frame filtering, flash-owner interlock, SWD note), the dated research/decision document, and byte-exact reference artifacts (stock hex, reference linker script) for verification and unbricking.
- **scripts/** — Linux build helper (`ci-build.sh`): fetches the gitignored deps and runs the Make build + size gate.
- **.github/** — GitHub Actions workflow that builds the firmware on push/PR and publishes a release titled `c-cpp/ra4m1 vX.Y.Z` on `c-cpp-ra4m1-v*` tags.
- **vendor/** — Vendored third-party build inputs:
  - Arduino's `arduino-renesas-bootloader` fork, where `src/` is integrated: boot decision, `boot5()` jump, flash HAL, checked DFU callbacks, CAN service loop, GPIO status LED, and `can_diag.{c,h}` for the bench-only `CAN_DIAG` build;
  - tinyusb 0.17.0, whose RA `fsp.ld` places `.text.boot_low_flash` below the option bytes and whose `ra4m1_minima_boot.ld` bounds the bootloader to 16 KB;
  - Renesas FSP, ARM CMSIS_5, and standalone RA4M1 device headers.

The pure-logic `src/boot/` core is developed and tested on the host, then compiled into the vendored `arduino-renesas-bootloader` fork (behind the `CAN_LOADER` and `DFU_CUSTOM_NAME` Makefile flags) to produce the firmware image. `tools/can-flash/` is the host counterpart that speaks the CAN update protocol to the flashed device.
